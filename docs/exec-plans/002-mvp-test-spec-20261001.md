## 판정 규칙

`PASS`: 실행한 기대 결과가 일치하고 증거가 있다. `FAIL`: 재현된 불일치. `BLOCKED`: 서버/계정/결정/파일이 없어 실행할 수 없다. `NOT RUN`: 아직 실행하지 않았다. mock 통과는 mock 범위의 PASS이며 live 검증을 대신하지 않는다. disabled/empty 화면 검증은 해당 회귀만 증명한다.

새 테스트 파일은 예정 산출물이다. 현재 존재하는 파일을 확장할 때는 기존 테스트를 삭제/약화하지 않는다. 신규 unit 파일은 runner 발견 검증에도 포함한다. 새 도구 의존성은 미리 확정하지 않는다.

단계별 검증은 `T10/학생 preview`, `T10/교사`, `T10/도서관`, `T10/PDF`처럼 하위 증거를 기록한다. S04에서는 제공된 학생 화면까지만 판정하고 후속 화면은 S11 통합 대장으로 이월한다. T12의 PDF, T13의 익명 접근, T14의 교사 현황, T17의 외부 cache도 동일하다. 필요한 하위 검증이 모두 PASS여야 T 전체가 PASS다. T13/T17 외부 검증은 같은 slug가 공개 on에서 익명 200과 예상 본문을 제공하는지 먼저 확인한 뒤 off 차단을 검증한다. 처음부터 항상 404인 화면은 통과가 아니다.

## 환경과 데이터

- Mock: 공통 API origin fixture를 사용하고 미등록 백엔드 요청을 차단한다. 합성 JWT는 브라우저 UX 검증용이며 서명/권한 증거가 아니다.
- Live: 폐기 가능한 staging 학생 A/B·교사 T·만료/무효 토큰, 테스트 학년도/전공·문서·PDF job만 사용한다. 계정/리소스 준비는 D13을 따른다.
- 저장 데이터: 이름/학번/학과/이메일/한 줄·상세 소개/스택/링크/한글·영문 혼합 Markdown/PROFILE·PROJECT·FREE/순서가 다른 page ID/실제 PNG·JPEG·WebP/긴 문서/QR.
- 비동기 fixture: load/upload/save/refresh 응답을 명시적으로 지연/역순 완료하고 사용자 입력을 그 사이 발생시킨다. timer는 테스트 clock으로 조절한다.
- 모든 기능: loading/empty/error/success, 재시도, pending 중 중복 조작, 역할/소유권, 새로고침 후 결과 보존을 확인한다.
- 기록: SHA, runtime(Next 또는 Workers), 명령, 시작/종료, exit code, 실패 시 trace/screenshot, live 대상과 데이터 정리 결과. 토큰/비밀번호/메일 인증코드는 기록하지 않는다.

## 실행 명령과 순서

### T00 문서 대조 절차

1. `rg --files src/app src/features tests scripts .github/workflows`로 현재 파일을 확인하고 `package.json`, `playwright.config.ts`, `vite.config.ts`, `wrangler.jsonc`의 명령/런타임을 읽는다.
2. `rg -n '구현 전|추가 예정|HOLD|PDF 변환 책임|fixture|test:e2e|test:unit' docs README.md`로 오래된 문구 후보를 찾는다. 과거 QA/결정의 역사 기록은 삭제하지 않고 현재 상태와 연결한다.
3. `docs/index.md`, `REQUIREMENTS.md`, `TECH_STACK.md`, `DECISIONS.md`, `TESTING.md`, `LOCAL_ENVIRONMENT.md`, `DESIGN_SYSTEM.md`의 해당 문구/경로를 현재 파일과 행별 대조한다. Markdown 상대 링크는 문서 디렉터리 기준 존재를 검사하고 `path:line`은 파일 존재/줄 범위를 검사한다. 결과 목록과 수정 diff를 남긴다.
4. `git diff --check`와 R/S/T/D ID 참조 검사를 통과시키고, 오래된 문구 중 의도적으로 보존한 항목은 이유를 기록한다.

### T25 실제 PDF 내용 검사 절차

1. D10 해제 시 검사 도구와 실행 방법을 기록한다. 브라우저 내장 PDF 열람을 기본 수동 표면으로 사용하고, 자동 렌더/텍스트 추출은 PDF skill 및 번들 runtime에서 사용 가능한 도구를 확인해 절대 실행 경로·명령·버전을 고정한다. 도구 미확인 상태에서 렌더/추출을 수행했다고 기록하지 않으며 신규 라이브러리는 사용자 결정 없이 설치하지 않는다.
2. staging 학생 A의 한글 이름, 이메일, 한 줄/상세 소개, 글자 크기/Bold/인용, 클릭 가능한 링크, 실제 PNG와 JPEG, QR, 마지막 문단 `PDF-END-A`를 포함한 여러 페이지 문서를 저장한다. 저장 revision과 변환 job/result ID를 기록한다.
3. 결과 파일을 내장 PDF Viewer로 열어 페이지 수/한글 글꼴/첫·중간·끝 페이지/이미지/마지막 문단을 확인한다. 텍스트 추출 결과에서 이름·이메일·`PDF-END-A`를 비교하고 페이지 렌더로 clipping을 검사한다. 링크 클릭 대상과 QR 디코딩 결과는 원본 URL과 비교한다. 자동 도구가 없으면 동일 내용을 수동 검사하고 자동 검사는 별도 BLOCKED로 남긴다.
4. 파일 hash, job/revision, 도구/명령, 텍스트 비교 결과, 첫·끝 및 이미지/QR 페이지 capture를 증거로 남긴다. S09 PDF 파일 검사와 S10 이후 Viewer/다운로드 통합 검사를 구분한다.

### T30 반/학생 이동 fixture와 assertion

- mock 책은 총 8페이지: 1 표지, 2 목차, 3~4 학생 A(1반), 5 학생 B(1반), 6~8 학생 C(2반). Viewer 표시 기준은 1-based이며 서버 인덱스가 0-based이면 D10에서 변환 규칙을 확정한다. 예상 반 시작점은 1반=3, 2반=6이다.
- 초기 1페이지에서 A 클릭 -> 페이지 표시 3/8·A 본문, B 클릭 -> 5/8·B 본문, 2반 클릭 -> 6/8·C 본문을 assertion한다. A 내부 다음 페이지는 4/8이며 A 선택이 유지되어야 한다. C 마지막 페이지는 8/8이다.
- 이름 검색으로 B를 선택한 뒤 5/8 이동을 확인한다. 없는 학생/빈 인덱스/범위 밖 인덱스는 다른 학생 페이지로 이동하지 않고 오류/빈 상태를 표시한다. 숫자 카운터뿐 아니라 렌더된 학생 이름·첫 문단도 비교한다.
- 실제 서버 PDF에서는 인덱스와 파일을 받아 학생별 첫 페이지를 수동으로 확인해 expected 목록을 만든 뒤 같은 클릭·페이지·본문 assertion을 반복한다. mock의 8페이지를 실제 파일 페이지 수로 가정하지 않는다.

현재 존재하는 명령:

```bash
pnpm lint
pnpm test:unit
pnpm exec next typegen
pnpm typecheck
pnpm build
pnpm exec playwright test tests/e2e/student-resume-management.spec.ts --workers=1
pnpm test:e2e
```

`pnpm build`는 현재 `next build` 뒤 postbuild의 vinext build 및 Next typegen까지 실행한다(`package.json:8`). 전체 build 뒤 vinext build를 무조건 중복 실행하지 않는다. Workers 결과만 따로 검증할 때 `pnpm build:vinext`를 사용한다.

S01 mock 네트워크 격리 후, fresh 서버로 전체 E2E를 실행하는 현재 설정의 경로:

```bash
CI=1 PLAYWRIGHT_PORT=3114 pnpm test:e2e
```

위 CI 모드는 build를 다시 실행하지 않으므로 같은 SHA로 `pnpm build`를 먼저 완료해야 한다. `localhost`를 사용하며 임의 `127.0.0.1` origin으로 live CORS 결과를 일반화하지 않는다. 기존 port 사용 여부를 확인하고 fresh port를 선택한다. 다른 API origin을 사용할 때 fixture도 공통 설정을 따라야 한다. 현재 Playwright config는 원격 BASE_URL/staging 실행을 지원하지 않으므로 S01/S11에서 별도 명령/설정을 추가한 뒤 기록한다.

새 테스트 파일은 실제 생성된 이후에만 그 경로를 대상으로 실행한다. 현재 71개 시나리오 발견 결과를 통과 수로 기록하지 않는다.
