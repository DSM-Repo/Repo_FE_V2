# Git Workflow

Repo-V2의 커밋, 이슈, PR 작성 기준을 정리합니다.

## 커밋 메시지 컨벤션

Repo-V2는 이슈 번호를 기준으로 작업을 추적하기 위해 브랜치명과 커밋 메시지 형식을 고정합니다.

### 기본 형식

```txt
type (#이슈번호) :: 커밋 메세지
```

일반 작업은 이슈 생성 후 진행하므로 이슈 번호를 포함합니다. 이슈가 없는 예외 작업은 사용자가 명시적으로 허용한 경우에만 `type :: 커밋 메세지` 형식을 사용합니다.

### 강제 규칙

- 모든 작업 커밋은 `type (#이슈번호) :: 커밋 메세지` 형식을 반드시 사용합니다.
- 제목을 명사형 또는 결과 중심 구문으로 쓰더라도 `type`, 이슈 번호, `::` 구분자는 생략하지 않습니다.
- 이슈 기반 브랜치에서 작업 중이면 브랜치명의 이슈 번호를 커밋 제목에 그대로 사용합니다.
- 커밋 전 `git log -1 --pretty=format:%s` 또는 staged commit message 확인으로 형식을 검증합니다.
- 컨벤션을 벗어난 커밋은 PR 생성 전 `git commit --amend` 또는 interactive rebase로 메시지를 고친 뒤 올립니다.
- 사용자가 별도 문구를 요청해도 형식 prefix는 유지하고, 요청받은 문구는 `커밋 메세지` 영역에만 반영합니다.

### 예시

```txt
feat (#12) :: 문서형 이력서 에디터 초안 추가
fix (#18) :: 공개 상태 토글 동기화 오류 수정
docs (#21) :: 커밋 컨벤션 문서 추가
chore (#22) :: ESLint ignore 범위 정리
```

### 타입

허용 타입은 아래 목록으로 한정합니다.

| 타입 | 의미 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가, 기존 기능을 요구 사항에 맞게 수정 | 로그인 기능 추가 |
| `fix` | 기능에 대한 버그 수정 | 로그인 시 비밀번호 검증 오류 수정 |
| `build` | 빌드 관련 수정 | 빌드 도구 또는 버전 수정 |
| `chore` | 패키지 매니저 수정, 템플릿, `.gitignore` 등 기타 수정 | 이슈 템플릿 수정 |
| `ci` | CI 관련 설정 수정 | CI 검증 명령 추가 |
| `docs` | 문서 또는 주석 수정 | README 수정 |
| `style` | 코드 스타일, 포맷팅에 대한 수정 | 불필요한 코드 제거 |
| `refactor` | 기능 변화가 아닌 코드 리팩토링 | 함수 분리, 네이밍 정리 |
| `test` | 테스트 코드 추가 또는 수정 | E2E 테스트 추가 |
| `release` | 버전 릴리즈 | 버전 태그 준비 |

### 제목 작성 규칙

- 제목은 가능한 한 짧고 명확하게 쓴다.
- 커밋 내용은 명사형 또는 작업 결과가 바로 드러나는 짧은 구문으로 쓴다.
- `~한다`, `~했다`, `~하기` 같은 서술형 제목은 피한다.
- 명사형 제목 규칙은 `type (#이슈번호) ::` 형식보다 우선하지 않는다.
- 마침표로 끝내지 않는다.
- 한국어를 우선 사용하되, 타입/파일명/API/컴포넌트명 등 영어가 자연스러운 부분은 영어를 사용한다.

## 본문 작성 규칙

본문은 선택 사항입니다. 별도 설명이 없어도 커밋 의도가 명확하면 작성하지 않습니다.

본문이 필요한 경우에도 최대한 간단히 작성합니다.

```txt
feat (#12) :: 문서형 이력서 에디터 초안 추가

에디터 저장 포맷 비교를 위해 최소 기능만 연결한다.
```

## Footer / Trailer

이슈 자동 연결이 필요하면 footer에 GitHub 키워드를 사용할 수 있습니다.

```txt
Closes: #12
```

의사결정 맥락이 중요한 커밋은 필요한 trailer만 짧게 남깁니다.

```txt
Constraint: PDF 변환 방식은 아직 확정하지 않음
Tested: pnpm lint; pnpm build
```

## Issue / PR 운영

Issue와 PR은 가능하면 GitHub CLI 또는 GitHub UI로 생성합니다.

### Issue

- 퍼블리싱, 디자인 시스템, UI 컴포넌트 작업은 전용 Issue Form으로 생성한다.
- 기능/버그/문서/기술결정 유형은 필요해지는 시점에 별도 템플릿 분리를 검토한다.
- 커밋에는 가능하면 관련 이슈 번호를 포함한다.


### Issue 기반 Branch / PR 흐름

Repo-V2의 일반 작업은 아래 순서를 기본으로 합니다.

1. GitHub Issue를 먼저 생성한다.
2. 이슈 번호를 포함한 작업 브랜치를 생성한다.
   - 형식: `type/#이슈번호-브랜치네임`
   - 예: `feature/#12-resume-editor`
   - 예: `fix/#18-public-toggle-sync`
   - 예: `hotfix/#19-login-blocker`
3. 해당 브랜치에서 작업하고 검증한다.
4. PR을 생성해 main으로 merge한다.
5. PR merge 후 로컬 main을 원격 main과 동기화한다.

예외:

- 인증 복구, 실패한 명령 재시도, 단순 상태 확인처럼 코드/문서 변경이 없는 작업
- 사용자가 명시적으로 main 직접 작업을 요청한 경우

### PR

- 기능 단위 또는 문서 단위로 작게 만든다.
- PR 제목은 가능하면 커밋 컨벤션과 유사하게 작성한다.
- PR 본문에는 변경 요약, 검증 결과, 남은 위험을 간단히 적는다.

## 현재 결정

- 브랜치명은 `type/#이슈번호-브랜치네임` 형식을 사용한다.
- 커밋 제목 형식은 `type (#이슈번호) :: 커밋 메세지`를 사용한다.
- 커밋 제목 형식은 필수이며, 명사형 요약 요청이 있어도 `type (#이슈번호) ::` prefix를 생략하지 않는다.
- type은 `feat`, `fix`, `build`, `chore`, `ci`, `docs`, `style`, `refactor`, `test`, `release`로 한정한다.
- 제목은 명사형 또는 작업 결과 중심의 짧은 구문으로 작성한다.
- 본문은 선택이며, 필요할 때만 짧게 작성한다.
- 퍼블리싱/디자인 시스템/UI 컴포넌트 작업은 GitHub Issue Form을 사용한다.

## GitHub Issue Template

퍼블리싱, 디자인 시스템, UI 컴포넌트 작업은 `.github/ISSUE_TEMPLATE/01-publishing-task.yml` Issue Form을 사용합니다.

- 작업 유형, 배경/목적, 디자인 기준, 범위, 완료 기준, 검증 방법을 필수로 남깁니다.
- blank issue는 기본적으로 비활성화합니다.
- template chooser 반영은 해당 파일이 GitHub 기본 브랜치에 push된 뒤 확인합니다.
